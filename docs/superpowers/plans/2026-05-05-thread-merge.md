# Thread Merge Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extend the existing `MergeThreadInto` / `SplitThread` commands so that merging an event thread into a discussion thread (or any thread→thread merge) preserves the source's identity on its own row, copies the right fields onto the target, and survives connector re-sync. Adds a `merged_into_thread_id` back-reference column on `thread`, plus audience union, importance/urgency max, server-side `(twist_id, key)` migration via trigger, note-key collision handling, and `thread_association` repointing.

**Architecture:** Source thread is archived but otherwise untouched — its row is the snapshot. Target absorbs source's content (notes, links, schedules, tags) and identity-ish fields (audience, importance/urgency) at merge time. `(twist_id, key)` migrates between rows via a server-side `AFTER UPDATE` trigger because those columns aren't synced to clients. Split discovers source(s) via reverse-lookup on `thread.merged_into_thread_id` and uses set-subtract on audience to undo the merge. Many sources can merge into one target. Spec at `docs/superpowers/specs/2026-05-05-thread-merge-design.md`.

**Tech Stack:** Flutter/Dart (`apps/plot/`), Drift (SQLite, client-side store), Atlas (Postgres migrations), Kysely (TS workers). Pure helpers tested with `flutter_test`; integration verified manually + `flutter analyze`.

Create `libs/db/schema/95-triggers/40-transfer_twist_key_on_merge.sql`:

```sql
-- Server-side migration of (twist_id, key) when a thread is merged into
-- another. Runs on every transition of `merged_into_thread_id`:
--
--   NULL → set (merge):
--     - Source must also be archived in the same UPDATE (precondition).
--     - If source has (twist_id, key) and target has none, copy them
--       onto target. The partial unique index `thread_twist_key_unique`
--       is satisfied because source.archived_at is now set.
--     - If target already has its own different (twist_id, key), skip
--       silently. The connector-duplicate behavior remains in this
--       rare case (no regression vs pre-merge baseline).
--
--   set → NULL (split):
--     - Source must also be unarchived in the same UPDATE (precondition).
--     - If target.(twist_id, key) == source.(twist_id, key), clear them
--       from target so source can reclaim the active key slot. Order:
--       AFTER UPDATE on source — Postgres has already applied the
--       unarchive, so we update target while source holds the key. To
--       avoid a transient duplicate-active-key state, we use a deferred
--       constraint isn't required because the AFTER UPDATE runs after
--       all row-level updates land but before statement commit; we
--       UPDATE target inside the trigger and the index check happens at
--       statement end across both rows.
--
-- Twist_id and key are not synced to clients, so all of this happens
-- transparently from the Flutter app's perspective.
CREATE OR REPLACE FUNCTION transfer_twist_key_on_merge ()
    RETURNS TRIGGER
    LANGUAGE plpgsql
    AS $$
DECLARE
    v_target_twist_id bigint;
    v_target_key text;
BEGIN
    -- Merge: NULL → set
    IF OLD.merged_into_thread_id IS NULL AND NEW.merged_into_thread_id IS NOT NULL THEN
        IF NEW.archived_at IS NULL THEN
            RAISE EXCEPTION 'thread merge requires archived_at to be set on source';
        END IF;
        IF NEW.twist_id IS NULL OR NEW.key IS NULL THEN
            RETURN NEW;
        END IF;
        SELECT twist_id, key
        INTO v_target_twist_id, v_target_key
        FROM thread
        WHERE id = NEW.merged_into_thread_id;
        IF v_target_twist_id IS NULL OR v_target_key IS NULL THEN
            UPDATE thread
            SET twist_id = NEW.twist_id,
                key = NEW.key
            WHERE id = NEW.merged_into_thread_id;
        END IF;
        -- If target already has its own different (twist_id, key), do nothing.
        RETURN NEW;
    END IF;

    -- Split: set → NULL
    IF OLD.merged_into_thread_id IS NOT NULL AND NEW.merged_into_thread_id IS NULL THEN
        IF NEW.archived_at IS NOT NULL THEN
            RAISE EXCEPTION 'thread split requires archived_at to be cleared on source';
        END IF;
        SELECT twist_id, key
        INTO v_target_twist_id, v_target_key
        FROM thread
        WHERE id = OLD.merged_into_thread_id;
        IF v_target_twist_id IS NOT NULL
            AND v_target_key IS NOT NULL
            AND v_target_twist_id = NEW.twist_id
            AND v_target_key = NEW.key THEN
            UPDATE thread
            SET twist_id = NULL,
                key = NULL
            WHERE id = OLD.merged_into_thread_id;
        END IF;
        RETURN NEW;
    END IF;

    RETURN NEW;
END;
$$;

CREATE TRIGGER transfer_twist_key_on_merge
    AFTER UPDATE OF merged_into_thread_id ON "public"."thread"
    FOR EACH ROW
    EXECUTE FUNCTION transfer_twist_key_on_merge ();
```

import 'package:plot/store/store.dart';

/// Returns the union of [target] and [source] preserving target's order,
/// then appending any ids from source not already present.
///
/// Returns null if the union is empty.
List<Uuid>? mergeAudienceUnion(List<Uuid>? target, List<Uuid>? source) {
  final result = <Uuid>[...?target];
  final seen = result.toSet();
  if (source != null) {
    for (final id in source) {
      if (seen.add(id)) result.add(id);
    }
  }
  return result.isEmpty ? null : result;
}

/// Returns target with ids removed that only [source] contributed —
/// i.e. ids in source that no [otherActiveSources] entry carries.
///
/// Lossy in the rare case where a contact was in both the pre-merge
/// target and source: that overlap is dropped.
///
/// Returns null if the result is empty.
List<Uuid>? splitAudienceSubtract({
  required List<Uuid>? target,
  required List<Uuid>? source,
  required List<List<Uuid>?> otherActiveSources,
}) {
  if (target == null || target.isEmpty) return null;
  if (source == null || source.isEmpty) {
    return List<Uuid>.from(target);
  }
  final keptByOthers = <Uuid>{};
  for (final other in otherActiveSources) {
    if (other != null) keptByOthers.addAll(other);
  }
  final remove = source.where((id) => !keptByOthers.contains(id)).toSet();
  final result = target.where((id) => !remove.contains(id)).toList();
  return result.isEmpty ? null : result;
}
```

/// Lower rank = more urgent. Mirrors notification_service._urgencyRank
/// so urgency rules stay consistent across merge and notification paths.
int _urgencyRank(String? urgency) => switch (urgency) {
      'interrupt' => 0,
      'inform-requests' => 1,
      'inform-updates' => 2,
      'passive' => 3,
      _ => 4,
    };

/// Returns the more urgent of [a] and [b]. Null/unknown values are least
/// urgent and lose to any recognized urgency.
String? mergeUrgencyMostUrgent(String? a, String? b) {
  final ra = _urgencyRank(a);
  final rb = _urgencyRank(b);
  if (ra <= rb) return ra == 4 ? null : a;
  return rb == 4 ? null : b;
}

/// Returns the larger of two importance values. Defined here so merge code
/// reads symmetrically with the urgency helper.
int mergeImportanceMax(int a, int b) => a >= b ? a : b;
```

/// Returns the ids of source notes whose `key` collides with a key already
/// present on the target. Caller must null those keys when moving the notes
/// to satisfy the `note_thread_key_unique` constraint.
Set<Uuid> noteKeysToNullForMerge({
  required Map<Uuid, String?> sourceNoteKeys,
  required Set<String> targetExistingKeys,
}) {
  final result = <Uuid>{};
  for (final entry in sourceNoteKeys.entries) {
    final key = entry.value;
    if (key == null) continue;
    if (targetExistingKeys.contains(key)) result.add(entry.key);
  }
  return result;
}

## Notes for the engineer

**Context Plot expects you to know:**

- `Store.get` is the global Drift database; `db.threads` / `db.notes` / etc. are auto-generated table accessors. `db.add(table, companion)` performs an upsert (insert-or-replace by primary key).
- `Thread.copyWith(...).save()` writes through the Thread accessor, marks the row dirty for sync push, and triggers any side-effects (recompute preview etc.). `db.add(threads, row.toCompanion(false))` writes the raw row directly without those side-effects — used for merge so we don't trip preview/title regeneration.
- `Value<T>(...)` (re-exported from drift via `package:plot/util/value.dart`) is used to distinguish "set to null" (`Value(null)`) from "leave unchanged" (`const Value.absent()`) in `copyWith` calls. **You must use this distinction correctly** — passing `null` directly will be rejected at compile time.
- The Flutter app uses `forui` widgets and forbids `package:flutter/material.dart`. The merge command does not surface a UI error for `(twist_id, key)` conflict — the server trigger silently keeps both rows' values in that rare case.
- Sync push: `SyncOrchestrator.instance.push(SyncOrchestrator.thread)` flushes pending thread writes to the API. The merge command pushes `note` and `thread` separately; `thread` covers the source's `merged_into_thread_id` write and the target's identity updates.
- Database schema: the partial unique index `thread_twist_key_unique` is `WHERE archived_at IS NULL AND twist_id IS NOT NULL AND key IS NOT NULL`. Archived rows are not in it, so an archived source can keep its (twist_id, key) while target also has them.

**If a step fails:**

- Migration generation (`pnpm gen-migration`) failures: usually a SQL syntax error in the schema files. Fix the schema file, re-run.
- Migration apply failures: edit the generated `.sql` file directly. Re-run `pnpm apply-migrations`. Run `atlas migrate hash --dir file://libs/db/migrations` if you edited a migration file by hand.
- `flutter analyze` errors about `equalsValue`, `equals`, or column types: regenerate Drift code with `flutter pub run build_runner build --delete-conflicting-outputs`.

**What's NOT in this plan (deliberately):**

- Three-way merge UI.
- Restoring `importance` / `urgency` / `thread_association` on split.
- Adding an "absorb…" entry point on the target side.
- Per-merge audit log of which fields were absorbed.

These are listed as out-of-scope in the spec.
